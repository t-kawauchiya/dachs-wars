# 決定事項

決めたことと、その理由を残す。変えるときは消さずに「変更」として追記する。

## 技術選定（2026-11-25）

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 言語 | TypeScript | ルールや数値が増えても壊れにくくするため |
| ゲームエンジン | Phaser | シーン、入力、音、アニメーションが揃っていて、演出を早く作れる。ブラウザゲームの定番で、ポータル向けの情報も多い |
| 設計 | ロジックを分離し、決定的に作る | ルールを純粋なTypeScriptで書き、テストやCPUの先読みに使う。同じ入力からは必ず同じ結果になるので、リプレイ、オンライン対戦、不具合の再現が後から足せる |
| ビルド | Vite | TypeScriptがそのまま動き、Phaser公式のテンプレートもある。Vitestと設定を共有できる |
| UI | 全部Phaserの中で描く | ポータルの16:9枠、全画面、スマホの回転でも、全体が一緒に拡大縮小されてズレない |
| 照準 | ドラッグ操作（引っ張って離す） | スライダーが要らなくなり、スマホでも遊びやすい |
| パッケージマネージャー | pnpm | 速く、依存関係の管理が厳密。ワークスペース機能を使う |
| テスト | Vitest | Viteの設定をそのまま使える。テストの主役はcoreの純粋な関数 |
| lint・フォーマット | Biome | 1つのツール、1つの設定でlintとフォーマットの両方をこなせる |
| 弾道・当たり判定 | core側で自作 | 決定的に作るため、エンジンの物理には頼らない |
| 音 | Phaser内蔵の音機能 | 追加ライブラリが不要 |
| ホスティング | Cloudflare | 静的ファイルの公開から始め、オンライン対戦（Workers＋Durable Objects）、ユーザー管理（D1＋認証）を段階的に足せる。サーバーもTypeScriptで書ける |
| リポジトリ構成 | pnpmワークスペース | coreをクライアントとサーバーで共有するため |
| CI | GitHub Actions | push・プルリクごとにBiome、型チェック、Vitestを回し、Cloudflareへのデプロイもまとめる |

## 設計の方針

- `core` は Phaser にもブラウザにも依存しない純粋な TypeScript。
- 状態は `step(state, action) → { state, events }` で進める。乱数はシード付き。
- `events` は「何が起きたか」の列（弾の軌道、食べた、腰にダメージ、寝た など）。描画側はこれを順に演出するだけで、状態の差分を推測しない。
- オンライン対戦では、サーバーが同じ `core` を動かして正しい状態を持つ。

```
packages/
  core/     ルール（クライアントとサーバーで共有）
  client/   Phaser（表示と入力）
  server/   Cloudflare Workers（オンライン対戦を作るときに追加）
```

## ゲームの柱（2026-11-25）

ルールを足すか削るかは、この柱を引き立てるかどうかで判断する。

1. 食べ物で釣って、段差を登らせて、腰をやらせる
2. 背中に砲台を背負ったダックスが可愛い
3. 腰を痛めて辛そうにしている姿が見られる

## ゲームルールの決定（2026-11-25）

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 砲台の役割 | 餌をまく装置。撃った食べ物は地面に落ちて餌になり、相手に直接当てて倒すものではない | 直接当てるほうが早いと誰も釣らなくなり、柱1が死ぬため |
| 犬の移動 | プレイヤーは動かせない。犬は近くの餌に勝手に釣られて動く | 釣りをゲームの中心に据えるため |
| プレイヤーの行動 | 餌を撃つ、段差を置く | |
| 足と砲台 | 試合前の組み立てで選ぶ（戦闘中には変えない） | |
| 近接攻撃（ぺろぺろ）、押し出し | v1では入れない | 釣りが中心になり、不要になった |
| 食べ物のパラメータ | 飛距離、におい（何マス先の犬まで気づかせるか）、食いつき（その餌に向かって1ターンに何マス進むか）、満腹感（体重の増え方も比例） | 食べ物ごとの性格の違いを遊びどころにするため |
| 砲台 | 1門につき食べ物1種類を積む（1〜3門）。多いほど重くなり、段差ダメージが増える | 背中の砲台に違う食べ物が詰まっている見た目が可愛い。v2で食べ物が増えると「何を積むか」の選択になる |
| 足 | 4〜10本。多いほど段差ダメージは減るが、1ターンの移動距離が伸びて餌に飛びつき、食べすぎる | 足が多い＝寝やすい犬、足が少ない＝腰をやりやすい犬、という勝ち方のトレードオフになる |
| 組み立ての縛り | ポイント制にはせず、上限とトレードオフだけで縛る | 足も砲台も、増やすほど得になる構造になっていないため |
| 1ターンの移動マス数 | 食べ物の食いつき ＋ 足による補正 | |
| 段差を置く | 犬と餌がないマスならどこでも置ける。1回で1段。隣のマスとの高低差が2段を超える置き方はできない | どこでも必ず登れるようにして、「釣って、登らせて、腰をやらせる」が常に成立するようにする。閉じ込めによる膠着を防ぐ |
| 試合の長さ | 1試合3〜5分、それぞれ8〜12ターンで決着するのを目安に数値を調整する | ポータルでは短く何回も遊ばれるほうが合う |
| 決着しないとき | ターン上限（仮に15ターン）。上限に達したら、負けまでの余裕（腰の残りと、満腹100までの残りの小さいほう）が大きい方の勝ち。同じなら引き分け | |
| 先攻 | ランダム。遊んでみて偏りがあれば対策する | 後攻は相手の餌を見てから動けるので、先攻が必ず有利とは限らない |
| 決着の演出 | 負けた側（腰で退場、満腹で寝る）に加えて、勝った側も褒められて嬉しそうにする演出を入れる | |
| v1の範囲 | CPU戦と1台での2人対戦、ステージ1つ、犬1種類、食べ物3種、PCとスマホ（横向き） | まず小さく公開して反応を見る |
| 1ターンの流れ | 手番のプレイヤーが「餌を撃つ」か「段差を置く」を1回 → 両方の犬が餌に釣られて動く → 餌に着いたら食べる → 相手の手番 | |
| 地形の表し方 | マス目（列ごとの高さ） | ルールが全部マスと段で決まっているので、そのまま書ける。決定的に作るのも簡単 |
| 画面 | 横向き16:9、基準解像度1280×720。比率が合わない画面ではPhaserの`FIT`で全体を収め、余白は帯で埋める。縦持ちのスマホには「横にしてね」と表示 | ポータルでよく使われるサイズで、PCでもスマホでも拡大縮小しすぎない |
| 絵の作り方 | パーツを組み立てる。胴体、頭（表情違い）、しっぽ、足、機械の足、砲台、食べ物を別々のSVGで用意し、コードで組み立ててトゥイーンで動かす。見た目はプロトタイプの雰囲気をベースにする | 足4〜10本×砲台1〜3門×表情の組み合わせをコードに任せ、絵は部品ごとに描けば済む。SVGはどの解像度でもくっきりし、後から差し替えやすい |
| 食べ物の種類（v1） | ジャーキー（飛距離長・におい短・食いつき弱・満腹中）、チーズ（飛距離中・におい長・食いつき強・満腹小）、さつまいも（飛距離短・におい中・食いつき中・満腹大） | 遠くからじわじわ誘う／一気に引っ張る／太らせて寝かせる、で役割を分ける |
