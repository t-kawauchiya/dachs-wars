# 開発フロー

Issue、ブランチ、プルリク、CI の決め事はこのファイルにだけ書く。AGENTS.md、テンプレート、スキルには中身を書かず、このファイルを参照させる。決め事を変えるときは、このファイルを直すプルリクを出す。

## 流れ

1. Issue: 目的、完了条件、変えてはいけないことを書く
2. ブランチ: main の最新から切る
3. 設計: `/architect with checkpoint` で計画を出し、オーナーが承認してから実装に入る
4. 実装: `/poteto-mode` に Issue の内容を渡す
5. 手元で検証: チェックを全部回し、差分が Issue の範囲に収まっているかを確かめる
6. プルリク: テンプレートどおりに本文を書き、`Closes #番号` を付ける
7. CI: プルリクを出すと自動で走る
8. レビュー: `/interrogate` の指摘をオーナーが読んで判断する
9. マージ: オーナーが Squash merge する

## Issue

- 1つの Issue を1つのプルリクで閉じる。プルリクは15分ほどでレビューできる大きさにする。収まらないときは Issue を分ける
- 目的、完了条件、変えてはいけないことの3つを必ず書く
- 完了条件は、実装のときに `/poteto-mode` の `Done means` にそのまま渡す。そのため、確かめられる形で書く（例: 「`pnpm test` で段差ダメージのテストが通る」）
- 起票は GitHub の画面のフォームか、`/new-issue` で行う

## ブランチ

- 名前は `<種類>/<Issue番号>-<内容>` にする（例: `feat/12-core-types`）。種類はタイトルの種類と同じものを使う
- main の最新から切る。前のプルリクの変更が必要な作業は、そのプルリクがマージされてから切る
- main に直接コミットも push もしない

## タイトル

コミットとプルリクのタイトルは `種類(scope): 説明` の形にする（例: `feat(core): 状態とアクションの型を追加`）。Squash merge なので、プルリクのタイトルがそのまま main のコミットになる。

| 種類     | 使う場面                                  |
| -------- | ----------------------------------------- |
| feat     | 機能を足す                                |
| fix      | 不具合を直す                              |
| refactor | 動きを変えずにコードを整理する            |
| test     | テストだけを足す、直す                    |
| docs     | 文書だけを変える                          |
| chore    | 設定、依存、CI など、上のどれでもない作業 |

| scope  | 対象                                    |
| ------ | --------------------------------------- |
| core   | `packages/core`                         |
| client | `packages/client`                       |
| infra  | CI、GitHub の設定、ツールの設定、スキル |
| docs   | README と `docs/`                       |

- scope は必ず付ける。ラベルとマイルストーンは使わず、scope で分ける
- 説明は日本語で書く

## 設計

- すべての作業で、実装の前に `/architect with checkpoint` で計画を出す。オーナーが承認してから実装に入る
- 計画を出す前に、作業に関係する設計の文書を読む。Issue を書くときも同じ文書を読み、完了条件をルールに合わせる

| 作業                                                          | 読む文書               |
| ------------------------------------------------------------- | ---------------------- |
| ゲームのルール、操作、画面に関わる作業（主に core と client） | `docs/game-design.md`  |
| パッケージの構成、ライブラリ、CI、ホスティングに関わる作業    | `docs/architecture.md` |

- ルールや設計の方針を変えたときは、同じプルリクで上の文書も更新する

## 実装

- `/poteto-mode` に、Issue の目的、完了条件、変えてはいけないことを渡す

## 手元で検証

プルリクを出す前に、次の3つを確かめる。

1. `pnpm check`、`pnpm typecheck`、`pnpm test`、`pnpm build` が通る
2. 画面が関わる作業は、`pnpm dev` で実際に動かして確かめる。ビルドが通っただけでは完了にしない
3. `git diff --stat origin/main...HEAD` で、変わったファイルが Issue の範囲に収まっているかを確かめる。範囲外のファイルがあれば、プルリクを作らずにオーナーに知らせる

## プルリク

本文はテンプレートに沿って、次の5つを書く。

- 変更内容: 何を変えたか
- 理由: なぜ変えたか
- 検証: 何をどう確かめたか
- 振り返り: 下の3つに答える
  - `/architect` で計画が変わったか（変わったなら何が）
  - `/interrogate` で本物の指摘があったか（あったなら何が）
  - 手間の感覚（重かった、ちょうどよい、軽かった）
- `Closes #番号`

## CI

- プルリクと main への push で、`pnpm install --frozen-lockfile`、`check`、`typecheck`、`test`、`build` を順に実行する
- プルリクのタイトルが「タイトル」の節の形になっているかを確かめる
- CI が緑でないプルリクはマージできない

## レビュー

- すべての作業で `/interrogate` を実行し、オーナーが指摘を一つずつ読んで、直すかどうかを決める
- 直さないと決めた指摘は、理由をプルリクにコメントで残す
- わからない指摘や変更は `/teach` で説明させる

## マージ

- マージ方法は Squash merge だけにする。コミットメッセージはプルリクのタイトルと本文にする
- マージ後、ブランチは自動で削除される
- マージするかどうかはオーナーが決める。LLM はオーナーに頼まれたときだけマージする

## 決め事を守る仕組み

守らせたい決め事ほど、文章ではなく仕組みで止める。

| 仕組み                            | 止めるもの                                                                             |
| --------------------------------- | -------------------------------------------------------------------------------------- |
| GitHub のルールセット             | main への直接 push、プルリクを通さない変更、CI が赤いままのマージ、Squash 以外のマージ |
| CI                                | 形式に合わないプルリクのタイトル                                                       |
| フック（`.claude/settings.json`） | Claude Code が main の上で行う `git commit` と `git push`                              |

スキル（`/start-issue`、`/open-pr`、`/new-issue`）は、手順をこのファイルどおりに進めるための道具で、呼ばなければ働かない。決め事を強制するものではない。

## 見直し

振り返りが書かれたプルリクが5件たまったら、振り返りを読み返し、`/architect` と `/interrogate` を必須にする範囲を見直す。変えるときは、このファイルを直すプルリクを出す。
